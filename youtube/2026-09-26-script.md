## DuckDB Parquet — OFFSET Returns Wrong Data

**THE PROBLEM**

You've probably used LIMIT and OFFSET to build a paging API — it's so fundamental it barely feels like a design decision. You know the trade-off: OFFSET gets slow at high page numbers because it scans and discards everything before the boundary. Slow, but correct. You still get the right rows. That assumption breaks when your underlying data is Parquet files in DuckDB. DuckDB's columnar scan doesn't guarantee stable row ordering across executions when row groups are involved. The same query, run twice, can return different results.

**WHAT THEY DID**

Rusty's post benchmarked LIMIT/OFFSET versus `file_row_number`-based pagination on a 163-row-group Parquet file. `read_parquet` in DuckDB exposes a `file_row_number` virtual column giving each row's physical position. Using that for range-based pagination lets the engine skip entire row groups by reading only the metadata footer — no scan-and-discard. Result: 2.53x faster on that test file, and deterministically correct. Keyset pagination using `file_row_number` isn't just a performance optimization; it's the only correct pagination model for Parquet.

**MY TAKE**

The performance problem here is expected. The correctness problem is the one that should change your approach. OFFSET pagination assumes stable row ordering across executions — that's the semantic contract. Parquet row groups don't provide that guarantee. The bug is dangerous specifically because it's invisible: you get rows back, they look plausible, and nothing throws an exception. The deeper issue is that DuckDB's SQL interface makes Parquet feel like a relational table, but the row-ordering guarantees aren't the same. Any time an abstraction layer papers over a semantic difference in the underlying storage, someone is going to hit it in production. Here it just happens to be you, possibly already.

**THE TAKEAWAY**

Audit any paging API backed by Parquet files in DuckDB and replace OFFSET with `file_row_number` range queries. This is a correctness fix, not a performance one.

## EKS — Kubernetes Upgrade Rollback

**THE PROBLEM**

Kubernetes minor version upgrades have always had an asymmetric risk profile: the upgrade takes a maintenance window and changes real state, but the rollback is "recreate the cluster." That asymmetry pushed teams into defensive behaviors — delaying upgrades, skipping versions, building elaborate staging environments — not because upgrades go wrong often, but because the cost of reverting made the risk calculus unfavorable. Missing a version drift check or discovering an add-on incompatibility post-upgrade meant hours of incident work to undo something that should have been a cancellable operation.

**WHAT THEY DID**

EKS now supports in-place control plane rollback to the previous minor version within a seven-day window. Before initiating rollback, pre-rollback readiness checks verify version skew compliance across nodes and validate add-on compatibility. etcd data, workloads, and persistent volumes survive the operation intact. EKS Auto Mode extends this by automatically sequencing worker node rollback before the control plane reverts. No additional cost.

**MY TAKE**

The seven-day window is the right design decision — long enough to surface real production issues that only appear under live traffic, short enough that you can't defer the rollback decision indefinitely. What I'd verify before relying on the add-on compatibility check: it's only as good as the compatibility matrix it sources from. Third-party add-ons are the most common surprise in minor version upgrades, and "compatible" in the matrix and "compatible in your specific configuration" aren't always the same thing. Test your specific add-on versions against v1.37 in staging before the maintenance window.

**THE TAKEAWAY**

If upgrade delays in your Kubernetes lifecycle have been driven by rollback risk, that constraint is substantially reduced on EKS. Start running upgrades more aggressively — the cost of reverting dropped.

## Cloudflare — One AI Control Plane

**THE PROBLEM**

You're building a production AI application on Cloudflare. You want observability, rate limiting, and cost controls on every model call. You want a fallback provider without changing application code. But Workers AI and AI Gateway were separate products: inference you ran on Cloudflare's GPUs went through one endpoint; external providers you routed through AI Gateway went through another. Policy enforcement was split. Cost was tracked separately per product. Every time you added a provider, you added another accounting and monitoring surface.

**WHAT THEY DID**

Cloudflare unified Workers AI and AI Gateway into a single control plane behind one endpoint. Every provider — Cloudflare's own GPUs, Anthropic, OpenAI, Google — routes through the same API. Observability, caching, rate limiting, and security are configured once and apply across all providers. Prepaid credits consolidate into a single wallet. Model-first bindings let applications declare the target model and let the gateway resolve the actual provider, including failover, without any changes to application code.

**MY TAKE**

The unification removes the sharpest architectural seam in the previous model: the split between inference-you-own and inference-you-route meant your policy layer was inherently partial. One endpoint with one policy set is strictly better. The model-first binding approach is the piece I find most architecturally interesting — it's how you build provider-independent application code that survives vendor changes without a rewrite. The cost to watch: you're now betting on one horizontal control plane instead of multiple vertical ones. That's a reasonable bet, but it means Cloudflare's AI Gateway SLA is now your AI application's SLA, and that's a dependency worth making explicit.

**THE TAKEAWAY**

If you're managing separate observability setups per AI provider, consolidate to this model. Model-first bindings are the path to application code that doesn't need to know which provider it's talking to.

## Filestore on Colossus

**THE PROBLEM**

You're sizing shared filesystem storage for AI training or agent workloads. Your workload has high IOPS requirements and moderate storage needs — or lots of storage and bursty IOPS. On VM-backed NFS, those two dimensions are coupled: meeting an IOPS target often means buying capacity you don't need, because performance is proportional to provisioned size. For agent workloads where hundreds of processes are reading and writing shared state simultaneously, the over-provisioning penalty compounds quickly.

**WHAT THEY DID**

Google migrated Filestore from VM-based storage clusters onto Colossus — the distributed storage substrate running YouTube, Gmail, and Gemini. The key change: IOPS is now decoupled from capacity. Teams size performance and storage independently. Filestore multishares drop the minimum per-container allocation to 10 GiB. NFS file locking on Colossus supports high-concurrency agent workloads where many processes operate on shared state without consistency failures.

**MY TAKE**

Decoupling IOPS from capacity is the correct architectural direction for any storage system serving mixed workloads, and the fact that Google is running Filestore on the same substrate as their core products is a meaningful signal about where the platform is heading. The operational implication for AI teams is concrete: you can right-size your IOPS budget without paying for a storage footprint you don't need. The migration caveat is real — teams on VM-based Filestore should evaluate actual workload requirements against the new tier structure before migrating, because "decoupled" in the product docs and "decoupled at your specific access pattern" sometimes require tuning.

**THE TAKEAWAY**

For new AI workloads on GCP that need shared filesystem access, Filestore on Colossus is the correct default. Size IOPS and capacity independently from day one rather than letting IOPS requirements inflate your storage bill.

## Developer Device Platform

**THE PROBLEM**

Your mobile CI pipeline runs tests on two emulator configurations. AI coding agents generate code and tests faster than your device fleet can run them. Your agent's test environment in CI differs from your developer's local environment and both differ from the real device mix your users run. You have three testing planes that aren't connected, and adding a fourth — dedicated AI agent testing — makes the problem worse, not better.

**WHAT THEY DID**

Google Cloud's Developer Device Platform entered public preview as testing infrastructure built around agentic workflows. The Device Run API fans tests across hundreds of real and virtual devices simultaneously with smart sharding. Auto-retry targets specific failing tests rather than rerunning entire suites. A dedicated agent skill lets AI coding agents execute multi-step user journeys — validate hardware-specific behavior, spot visual artifacts, check on-device chip performance — without human supervision. It replaces Firebase Test Lab. The structural design decision: the same MCP tool interface external coding agents call — Claude, Cursor, Codex — is the same interface DDP's own built-in agent uses. One tool surface, two access modes.

**MY TAKE**

The MCP-first design is the decision that matters architecturally. By surfacing the same interface to both external and internal agents, Google is making the tool layer — not the platform's own intelligence — the thing that gets reused. The alternative is a walled-garden testing platform that requires a custom integration per AI toolchain. A unified MCP surface also means your policy enforcement happens in one place, regardless of which agent is running the tests. What I'd watch: whether the MCP interface stays stable across platform updates. Interfaces that serve both internal and external consumers have a history of API calcification. That's a constraint, not necessarily a dealbreaker.

**THE TAKEAWAY**

If you're building AI coding agent pipelines that touch mobile testing, evaluate DDP for the MCP interface first, not the device fleet size. Unified tool surfaces don't stay unified unless they're built that way.

## Kubernetes v1.37

**THE PROBLEM**

Your Kubernetes nodes are running containerd 1.7. You've been on 1.7 for a while because it works and a runtime upgrade hasn't been on the priority list. The v1.37 changelog flagged the containerd 2.0 requirement over a year ago. But the actual deadline is not the v1.37 GA date on August 26 — the deadline is the next time you need to upgrade your Kubernetes minor version, which might be sooner than you think if you're running security patches.

**WHAT THEY DID**

Kubernetes v1.37 requires containerd 2.0 or later. It graduates 28 tracked features, including the metrics.k8s.io API to Stable GA. Memory QoS with cgroup v2 moves to Beta and is enabled by default. The `kubectl run --filename` flag enters deprecation.

**MY TAKE**

The containerd requirement is the change that hits teams where the control plane upgrades automatically but node images don't — which is most managed Kubernetes deployments. If your node images ship containerd 1.7, upgrading to v1.37 requires a node image update on the same maintenance window as the control plane upgrade. That's more coordination than most teams budget for an incremental patch. The Memory QoS cgroup v2 change is the other one to verify: beta and on-by-default means you don't opt in — you opt out. JVM and Python heap-heavy workloads can behave unexpectedly when cgroup v2 memory limits are newly enforced. Run this in staging first.

**THE TAKEAWAY**

Check your containerd version and node images now. If you're on 1.7, get the runtime upgrade onto the next available node maintenance window before v1.37 forces the issue.
