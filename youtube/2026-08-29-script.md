## JioHotstar: 450M Ads in 100ms

**THE PROBLEM**

You've probably built a recommendation or selection pipeline with a latency SLO. Now imagine doing it for 450 million concurrent users during a live sports broadcast, where the selection window closes in 100 milliseconds and a miss means dead air. That's JioHotstar's ad decisioning problem during Indian Premier League matches — and the engineering tells you something important: ad decisioning is treated as a reliability-critical subsystem on the same tier as video delivery. Not an afterthought. Not a best-effort backend.

**WHAT THEY DID**

JioHotstar's distributed pipeline uses a waterfall tiering model across demand sources — first-party, programmatic, house ads — combined with PID and SHALE pacing algorithms to narrow thousands of candidates to a single 30-second ad pod per viewer. The system coordinates inventory, decisioning, content metadata, tracking, and analytics under the OpenRTB standard. The key architectural discipline: independent retry and failure isolation at every service boundary. A timeout in tracking never propagates to the video player. Ad decisioning fails gracefully to a house ad; playback never stalls.

**MY TAKE**

PID control for ad pacing is borrowed from industrial control theory and it's the right model here. You're not scheduling a fixed list — you're regulating delivery against a fluctuating signal. Demand across a live broadcast window is non-stationary: it spikes at break points, shifts by region, changes as the match progresses. A PID controller absorbs that variance without manual tuning that would be obsolete before the next match starts. What the post doesn't address: cold start. A first-time viewer with no history can't be personalized. At 450M subscribers that's a tail, but at those numbers it's a meaningful absolute count, and I'd want to know exactly where the floor is before JioHotstar falls back to non-personalized selection.

**THE TAKEAWAY**

If you're building real-time selection pipelines with hard latency SLOs, model pacing as a control system — not a rate limiter. PID-style feedback handles demand variance that static thresholds can't absorb, and the model is testable with off-the-shelf control theory tooling.

## Google Cloud Post-Quantum Roadmap

**THE PROBLEM**

Every TLS handshake your services negotiate, every code signature you verify, every certificate in your infrastructure depends on RSA or elliptic curve cryptography. Post-quantum computers will break both. Not "might break" — will break, on a timeline that's now inside the planning horizon of any infrastructure with a 10-year lifespan. The question is no longer whether to migrate. It's who does the work and when.

**WHAT THEY DID**

Google published a concrete PQC migration roadmap. ML-KEM hybrid key exchange is already live on all googleapis.com endpoints and all GCP load balancers. Cloud KMS now supports all three NIST PQC standards — ML-KEM, ML-DSA, SLH-DSA — for customer-managed keys. The delivery phases: SNDL harvest-now-decrypt-later risk elimination by 2027, integrity and non-repudiation by 2028, full platform coverage by 2029. Legacy algorithm deprecation — RSA, ECC — between 2030 and 2035.

**MY TAKE**

The shared responsibility split is the number to internalize. Google handles infrastructure-layer cryptography: your load balancers, your TLS termination, your managed services. You own everything else — updating your SDKs, renegotiating PQC handshakes at the application layer, reconfiguring your certificate authorities, migrating application-level signatures. In a 50-service architecture, that's not a sprint. It's potentially months of migration work across every service that generates a signature or negotiates a session. The 2030 deprecation date feels distant until you map out your actual migration scope and your historical migration cycle time. The planning window that avoids an emergency migration is 2026 to 2028. If you haven't started the inventory, you're already consuming that window.

**THE TAKEAWAY**

Run a cryptographic inventory now: which services generate signatures, negotiate sessions, or store long-term secrets? That inventory gives you your migration scope. Without it, you're planning a migration with no denominator.

## Azure AI Gateway: Inspect Every MCP Response

**THE PROBLEM**

You're deploying AI agents that call tools. Each tool is a different backend — Anthropic, OpenAI, Bedrock, Vertex AI, your own MCP servers. Each backend needs its own auth. Each is an injection vector. You have one agent fanning out across twelve backends simultaneously, and you need to observe, govern, and secure all twelve at once. Without a centralized policy point, that's twelve independent blast radii and twelve separate instrumentation problems.

**WHAT THEY DID**

Microsoft added a dedicated AI Gateway tier to Azure API Management, restructured around models, MCP servers, and tools rather than REST APIs. One endpoint fronts Anthropic, Bedrock, Vertex AI, and OpenAI. Per-backend auth — API key, OAuth 2.0, or managed identity — resolves at the gateway, not in agent code. The llm-content-safety policy now covers MCP tool calls and agent-to-agent payloads. And shield-prompt inspects inbound MCP server *responses* for adversarial prompt injection patterns — not just outbound requests from the agent.

**MY TAKE**

Inspecting inbound MCP responses is the detail most teams haven't built into their threat models yet. The attack vector is this: your agent calls a legitimate MCP server, that server's response contains embedded instructions that redirect the agent's behavior. Shield-prompt at the gateway intercepts that before it reaches the agent context. Most injection defenses focus on user input — this one focuses on tool responses, which is where the more sophisticated attacks will land. The XML-to-policy-card migration is also worth noting: it signals that AI traffic governance needs to be expressible without deep APIM XML expertise. Whether that reduces operational complexity in practice depends entirely on your policy complexity.

**THE TAKEAWAY**

The gateway is your policy enforcement point for multi-backend agent deployments. If you're not inspecting MCP responses for injection patterns, add that to your threat model before your agent count makes retroactive instrumentation painful.

## TelevisaUnivision: In-ISP Caching at 675M Views

**THE PROBLEM**

Live streaming is not on-demand streaming. You can't pre-warm caches if you don't know the exact demand shape. You can't smooth the audience curve. For TelevisaUnivision, the requirement was 104 live matches across 39 days, 100% availability, with peak audiences geographically concentrated in Latin America. Standard CDN PoPs put the cache one hop outside the ISP — one hop too far when the audience is that concentrated and that simultaneous.

**WHAT THEY DID**

Two structural decisions. First: in-ISP deep edge caching with direct peering to América Móvil and Telefônica — the two carriers covering most of TelevisaUnivision's audience — rather than relying on CDN PoPs outside ISP networks. Traffic absorbed at the ISP edge means the origin only sees cache misses. Second: session store migration to Memorystore for Valkey 9.0 running as serverless microservices with sub-millisecond authentication latency. Alongside that: pre-tournament stress testing and 24/7 joint war rooms with Google Cloud CRE during live matches. Result: 675 million cumulative views. Zero incidents.

**MY TAKE**

In-ISP caching is the CDN configuration your standard platform vendor doesn't expose to you. It requires carrier-level peering agreements and willingness to take on the operational complexity of caches inside ISP infrastructure. For most companies, that complexity isn't worth it. For events with audience demand concentrated inside a single carrier's network, the standard CDN model hits a wall that only ISP-level peering clears. The zero-incident claim across 39 consecutive days of live sports is also significant — live events at this audience scale have historically been where high-profile public failures happen.

**THE TAKEAWAY**

For marquee live events with geographically concentrated audiences, model the CDN-to-subscriber hop as the bottleneck — not your origin. In-ISP peering is the lever that standard CDN configuration won't give you.

## PostgreSQL Migration with Gemini

**THE PROBLEM**

Stored procedures are the reason most Oracle-to-PostgreSQL migrations stall. Schema migration is tractable. Data migration is tractable. But stored procedures written in PL/SQL with Oracle-specific semantics — NVL, DECODE, DBMS_OUTPUT, cursor handling, exception chains — require manual rewrite work that scales linearly with procedure count. If you have 500 stored procedures and not enough budget to manually rewrite them, the migration sits on the backlog indefinitely.

**WHAT THEY DID**

Google Cloud's Database Migration Service now uses a hybrid approach: a deterministic compiler handles 1:1 syntax mappings — NVL to COALESCE, DECODE to CASE, exception-handling rewrites — while Gemini handles complex procedural blocks using full schema context: cross-procedure call graphs, data type relationships, view dependencies. The key technical detail is a DFS-based call graph analysis that propagates result-set counts up the full procedure hierarchy. A stored procedure that calls another that calls another must be fully traversed before the translation target — PROCEDURE versus FUNCTION with SETOF refcursor — can be determined. The workflow stays inside IAM-governed Cloud project boundaries with mandatory staging before any production cutover.

**MY TAKE**

The DFS call graph traversal is what separates this from "paste your procedure into ChatGPT." Translation correctness for interconnected procedures requires resolving the full dependency tree first. Without it, you get locally correct translations that break at integration boundaries. The "months to days" claim is probably accurate for self-contained procedures and probably optimistic for deeply entangled ones with implicit cursor behavior and schema-specific state assumptions. The hybrid deterministic-plus-LLM approach is architecturally right: use exact compilation where the mapping is deterministic, LLM synthesis where it isn't. Building your own version of this? Invest in the call graph analysis step first.

**THE TAKEAWAY**

If stored procedure backlogs are blocking a migration, the hybrid deterministic-plus-LLM pattern is the right architecture. The call graph traversal is the non-negotiable piece — that's what makes the generated output correct across procedure boundaries, not just within them.

## ClickStack: Investigation-First AI Dashboards

**THE PROBLEM**

Ask an LLM to generate a dashboard in one shot and you get generic SQL against an imaginary schema. The model knows what dashboards look like. It doesn't know your actual data: your cardinalities, your query patterns, which columns are indexed, which joins are expensive. The result is a dashboard that's syntactically valid and semantically wrong for your specific deployment.

**WHAT THEY DID**

ClickStack's AI dashboard generation sends the model through an investigation phase before writing any SQL — querying the actual schema, examining query patterns, checking cardinalities — using the same MCP tool interface exposed to Claude, Cursor, and Codex. The MCP-first design creates a unified tool layer: the investigation the built-in AI does inside ClickStack is the same API surface an external coding agent would call. A dashboard workflow started in ClickStack is continuable in Cursor without format conversion. Full service-health, latency-by-endpoint, or error-grouped dashboards from a single natural language prompt.

**MY TAKE**

The investigation-before-generation pattern is the architectural takeaway, and it's replicable outside ClickStack. Any AI-assisted tool that generates schema-aware output benefits from an investigation phase over the actual schema before generation. The MCP unification is interesting — shared surfaces between internal AI and external agents is the right long-term direction. But a shared tool surface is also a shared blast radius. The post doesn't address what access controls govern what an external agent can discover through the same investigation interface a trusted internal agent uses. That's a question worth asking before you expose it.

**THE TAKEAWAY**

For any AI-assisted generation over data, build the investigation phase before the generation phase. Schema-aware generation is only as good as the schema understanding you give the model upfront — one-shot generation against documentation will always underperform against actual schema introspection.

## Java CPU Profiling Was Lying to You

**THE PROBLEM**

JFR's ExecutionSample event — the standard Java profiling mechanism — collected samples without weighting them to actual CPU time. Some hotspots appeared under-represented in your flame graphs. Others were over-represented. You optimized the method the profiler told you was hot. The real bottleneck was somewhere else. This wasn't a misconfiguration on your part. It was a structural bias baked into the sampling mechanism, and every major Java profiler was carrying it.

**WHAT THEY DID**

JDK 25 introduces a CPU-time profiling event that defers stack capture to a safe state between instructions and the next safepoint — rather than immediately unwinding at the signal-handler boundary. This eliminates the AsyncGetCallTrace dependency that async-profiler, Datadog's Java profiler, and JFR itself all relied on. That API was unsupported and breakable at any JDK update. The new mechanism produces accurate, proportional CPU sampling without any unsupported JVM internals. Native frame capture and on-demand stack capture for latency spikes are in the pipeline for future JDK releases.

**MY TAKE**

The safepoint-deferred approach changes the sampling model slightly: you're capturing the nearest safe state, not the exact moment of CPU activity. In tight loops with frequent safepoints, the difference is negligible. In code with long native call stretches, there's a potential gap between samples. That's worth understanding for workloads that mix JVM and native code heavily. But the bigger upgrade is removing AsyncGetCallTrace. Every Java shop was carrying a silent fragility — a dependency on an internal API that could break silently at any JDK release. That fragility is gone in JDK 25.

**THE TAKEAWAY**

Upgrade to JDK 25 and switch to the new CPU-time profiling event. Your previous flame graphs were directionally useful. Your new ones will be accurate. Those are different things and the difference matters when you're chasing a real bottleneck.
