## CosmosEscape: Own Every Azure Cosmos DB

**THE PROBLEM**

You've probably built something on a managed database service and assumed the sandbox was solid. The cloud provider handles isolation — your job is just writing queries. That assumption has a price, and CosmosEscape is the invoice.

**WHAT THEY DID**

Cosmos DB's Gremlin API compiles graph queries into .NET code at runtime. Wiz found that the .NET compilation sandbox failed to account for reflection — a well-known escape vector when you're running untrusted code. From reflection, they reached arbitrary code execution on the shared DB Gateway. From there, they extracted a master key. Not a key scoped to their account — a platform-wide key that granted full read and write access to every Cosmos DB account on the service. Wiz reported this in November 2025. Microsoft deployed a hotfix in 48 hours to close the Gremlin entry point. But eliminating the platform-wide credential model and rolling out per-account isolation across all regions took until July 2026 — eight months.

**MY TAKE**

The eight-month remediation timeline is the number to sit with. Blocking the entry point is fast. Rearchitecting away from a shared credential model — across a global service with millions of tenant databases — is an entirely different problem. And this wasn't exotic. Reflection as a sandbox escape is well understood. The failure was that the Gremlin sandbox never assumed the compiled code was adversarial. When you run untrusted input through a compiler, every language feature is an attack surface. The lesson for platform teams: defense-in-depth around any untrusted compilation path, and your blast radius model needs to account for what happens when the sandbox fails, not just whether the sandbox is theoretically sound.

**THE TAKEAWAY**

If your service compiles user-provided code or queries at runtime, your threat model needs to start one level above the sandbox: assume the sandbox fails and ask what the attacker can reach from the host process.

## Dogwood: Temporal Authorization for AI Agents

**THE PROBLEM**

You've probably wired up an AI agent with tool use and hit a hard question: how do you prevent it from doing something harmful? Rate limits help at the API layer. Scoped permissions help at the tool level. But neither approach can enforce "this agent can only call SendEmail after it has already called VerifyRecipient, and at most three times per ten-minute window." That's a sequence and a rate constraint over session history — and traditional authorization systems have no concept of time.

**WHAT THEY DID**

AWS open-sourced Dogwood, a Cedar extension that adds Metric First-Order Temporal Logic — MFOTL — to the policy layer. MFOTL is from the runtime verification literature, and it lets you write policies that reason about what an agent has already done in its current session: ordered prerequisites, rate limits over rolling time windows, escalation triggers. Dogwood composes with existing Cedar policies without migration, is Apache 2.0, and is integrated into Amazon Bedrock AgentCore Policy. The policy that would have required a bespoke session-state side channel in plain Cedar is a single Dogwood rule.

**MY TAKE**

This is the first serious attempt I've seen to put temporal authorization in the policy layer rather than application code. The problem is real and growing: stateless authorization was designed for human users where each request is independent. Agents have sessions — they accumulate state — and a permission model that ignores that is incomplete by design. The hard part of Dogwood isn't the formalism, it's the performance profile. MFOTL evaluation over session history is bounded by how much history you retain and how complex your policy graph is. They don't publish latency numbers, which is the number I'd want before committing this to a high-volume agent pipeline.

**THE TAKEAWAY**

If you're building AI agents with tool access today, design your authorization layer around session history from the start — even if you don't adopt Dogwood. Retrofitting temporal constraints onto a stateless auth model is going to be painful.

## Concurrency vs Throughput

**THE PROBLEM**

Your database is struggling. Queries are stacking up, latency is spiking, and your transaction pool is at the limit. The obvious move: raise the pool ceiling. More headroom, more concurrency, problem solved. Except at Vitess, they tried this — and it made everything worse.

**WHAT THEY DID**

A single long-running query blocked Vitess's vttablet transaction pool. The ceiling was around 1,000 connections. The instinct was to raise it to 10,000. But that eliminated the backpressure that vttablet uses to control admission to MySQL. Without the ceiling acting as a throttle, the entire queue of waiting requests flooded MySQL simultaneously — compounding the original problem. The fix was counter-intuitive: shrink the pool back to ~1,000. Restoring backpressure at the proxy layer let Vitess throttle inbound load before it reached the database engine, and throughput recovered.

**MY TAKE**

This is a classic queueing theory result playing out in production. Backpressure is not a safety valve you add when things are bad — it's load-shaping infrastructure that only works when it's always engaged. Once you exceed the concurrency level the downstream system can actually handle, raising the limit upstream doesn't increase throughput, it increases queue depth at the database layer and makes the problem harder to recover from. The insight about the proxy pool ceiling being a first-class architectural parameter is one I'd push teams to internalize: it's not a capacity ceiling, it's a rate control mechanism. The right ceiling isn't "how many connections can vttablet hold" — it's "how many simultaneous queries can MySQL absorb without degrading."

**THE TAKEAWAY**

Before you raise a connection pool limit to solve a throughput problem, model where the backpressure in your system actually lives. Removing it upstream moves the problem downstream and makes recovery harder.

## Meerkat: Global Consensus at 300 PoPs

**THE PROBLEM**

You've probably seen the Raft papers and thought: this looks clean, should work at scale. And it does — until your leader is in Virginia and half your replicas are in Tokyo, Sydney, and São Paulo. Raft's election timeout is designed for millisecond-scale latency. At intercontinental distances, you're measuring leader failures in seconds, and every leadership transition is an availability window where your system can't accept writes.

**WHAT THEY DID**

Cloudflare built Meerkat on QuePaxa — a 2023 consensus algorithm where all replicas can accept writes simultaneously. There's no leader to lose. Progress is never blocked by timeout expiry. Instead of a leader-follower model with lease-based elections, QuePaxa uses a diffuse ballot mechanism that degrades gracefully when replicas are partitioned from each other. Meerkat's current scope is intentionally narrow: control-plane metadata — database leadership grants, AI model placement decisions, routing rules — where correctness is non-negotiable and volume is manageable. This will be the first industrial deployment of QuePaxa at global scale.

**MY TAKE**

The narrow-scope launch is the right call. QuePaxa is a 2023 paper with no production track record. Deploying it on low-volume control-plane traffic first lets Cloudflare build operational experience before it's in the critical path for data-plane decisions. The architecture claim — every replica accepts writes simultaneously — sounds great in theory but the latency model changes completely: in Raft, reads from the leader are cheap; in QuePaxa, every write is a multi-round cross-replica coordination. The tradeoff is: better write availability under partition, potentially higher latency on every write. That's appropriate for Cloudflare's topology. It may not be appropriate for yours.

**THE TAKEAWAY**

If you're running consensus-dependent services across wide-area deployments, the leader-timeout failure mode is worth quantifying before assuming Raft-class algorithms are the only option. QuePaxa is worth tracking.

## Personal Repos and the Supply Chain You're Not Scanning

**THE PROBLEM**

You've probably got secret scanning running on your corporate GitHub organization. PRs get blocked on leaked credentials, security reviews check the commit history, SOC 2 auditors check the box. But 56% of the company-impacting secrets Wiz found weren't in your GitHub Enterprise org at all.

**WHAT THEY DID**

Wiz Research analyzed developer personal GitHub accounts across the Forbes AI 50 and found verified secret leaks in 65% of them. The attack surface is structural: engineers who push to a corporate org by day maintain side projects under personal accounts, and when corporate code or credentials get accidentally copied — via a fork, a git clone with secrets embedded in config, a half-finished refactor — they land outside every corporate scanning policy. AI-assisted development accelerates this because it increases code reuse and automated propagation faster than manual review can track. Wiz's detection approach correlates personal repos to corporate developer identities and validates actual secret risk before routing remediation to the owning developer.

**MY TAKE**

This is the supply chain problem that's hiding in plain sight. Secret scanning in enterprise environments is a known, solved-ish problem. Personal account correlation is not. What makes this particularly sharp is the AI angle — engineers who use AI coding assistants are moving code between contexts faster and with less awareness of what's being propagated. A snippet with a hardcoded credential that an engineer would notice in a manual copy-paste gets invisibly injected through a suggestion. The 65% number is brutal. If your security program stops at your org boundary, you have a gap this size.

**THE TAKEAWAY**

If you're running a security program for an engineering org today, personal repo correlation isn't optional anymore. Know where your developers have side projects and what's in them.

## WhatsApp On-Device AI: Scam Detection Without Reading Your Messages

**THE PROBLEM**

Scam detection at messaging scale sounds easy until you hit the constraints. You need to analyze message content. You can't send message content to a server — especially not at WhatsApp's billion-plus user scale, in jurisdictions with different data laws, on a platform built around end-to-end encryption. The naive architecture is impossible. The secure architecture has to be built from scratch.

**WHAT THEY DID**

WhatsApp's Scam Alert runs a lightweight ML model entirely on the user's device — zero message content leaves for inference. The model classifies incoming messages from non-contacts by analyzing conversational structure and linguistic patterns locally. The minimal telemetry needed to measure whether the feature actually works travels through a confidential federated analytics pipeline built on confidential VMs — a form of TEE — delivered as differentially private aggregates, never raw signal. The verifiability stack is the impressive part: model weights are published, manifests are signed by Cloudflare's transparency infrastructure, a third-party ledger records all model updates, and users can inspect an in-app audit log.

**MY TAKE**

The architecture is genuinely novel — the verifiability stack especially. Making every component independently auditable by security researchers, while shipping it to a billion users, is a hard problem that WhatsApp has solved cleanly here. The tricky part is the model distribution path. A device-side model that can be updated silently — even with a ledger — is a soft power tool. WhatsApp publishes the weights and the update ledger, which is the right call, but most users won't audit the ledger. The value is really for the research community. What I'd want to see next: open access to the differential privacy parameters, not just the model weights.

**THE TAKEAWAY**

If you're building any feature that needs behavioral signal from user communication at scale, on-device inference with federated analytics is the architecture to study. It's now production-proven at the billion-user level.

## Cloudflare MCP Security: Finding the Shadow Agents

**THE PROBLEM**

You're running enterprise AI agents. Your security team wants to know which MCP servers they're calling. The answer should be straightforward — except MCP traffic looks like HTTPS traffic. Your existing URL allowlists only catch servers you know about. Shadow MCP connections — agents calling unauthorized remote servers — are invisible at the network layer unless you're looking for them specifically.

**WHAT THEY DID**

Cloudflare Gateway now detects MCP at the protocol layer using a combination of three signals: hostname and path heuristics against known MCP server domains and wildcard patterns, DLP-based body inspection using regex against JSON-RPC method fields like `tools/call`, `prompts/get`, and `initialize`, and a new `experimental.is_mcp` selector triggered by the MCP-Protocol-Version header mandated by the 2025-11-25 spec and extended to every POST in the 2026-07-28 spec update. The practical output is the ability to surface shadow MCP traffic and enforce portal-only access or hard-block direct connections on managed network paths without touching MCP servers themselves.

**MY TAKE**

This is the right layer for this problem. Agent traffic needs the same visibility infrastructure we built for web traffic — and doing it at the network gateway rather than at each agent implementation means you don't have to instrument every agent separately. The limitation is the heuristic approach: detection relies on well-known domain patterns and header compliance. A non-compliant MCP server — one that doesn't send the MCP-Protocol-Version header — or a novel server that Cloudflare hasn't indexed won't be caught by the hostname heuristics. The body inspection path is more robust, but DLP scanning adds latency. For high-frequency agent tool calls, that's a meaningful tax.

**THE TAKEAWAY**

If your organization is deploying AI agents on managed networks, protocol-level MCP detection belongs in your security stack now — before shadow agents become a compliance finding.
