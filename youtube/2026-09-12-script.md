## CosmosEscape — Platform-Wide Azure Exploit

**THE PROBLEM**

You trust a managed cloud database service to isolate tenants. That's the entire security model — one customer's data cannot touch another's. Especially not Microsoft's, running Cosmos DB as a multi-tenant shared platform for hundreds of thousands of accounts, including their own internal services.

**WHAT THEY DID**

Wiz Research found that Cosmos DB compiled Gremlin graph queries into .NET code under restrictions that failed to account for reflection. A single reflection call gave code execution on the shared DB Gateway. From there, they extracted a master key that granted full read and write access to any Cosmos DB account on the service — including the databases backing Microsoft's own Entra ID, Teams, and Copilot. The only entry requirement was a standard Azure subscription with a Gremlin database. No elevated privileges. Obtainable in minutes. Microsoft deployed a hotfix to the Gremlin entry point within 48 hours of the November 2025 disclosure. But eliminating the platform-wide credential model — the actual architectural flaw — and rolling out per-account isolation across all regions took until July 2026. Eight months.

**MY TAKE**

The 48-hour hotfix timeline is fine. The eight-month structural remediation is the signal. When your trust model is baked into the platform layer — a shared master credential that spans all tenants — patching one entry point doesn't close the exposure, it just closes the path they demonstrated. Any other code-execution vector on that shared gateway was equally dangerous until the credential model was redesigned. The lesson is that sandbox escapes in multi-tenant managed services are a category of risk, not a one-off bug.

**THE TAKEAWAY**

If you're running multi-tenant infrastructure on shared compute, the threat model question isn't "is this input sanitized?" It's "if someone achieves code execution anywhere on this shared layer, what's the blast radius?"

## Vitess Backpressure Paradox

**THE PROBLEM**

You've got a database proxy, Vitess in this case, in front of MySQL. A long-running query blocks the transaction pool. Requests are queueing. The obvious move: raise the connection pool ceiling. More capacity should mean fewer blocked requests.

**WHAT THEY DID**

PlanetScale raised the vttablet transaction pool cap from roughly 1,000 to 10,000 during an incident. This removed the backpressure that was protecting MySQL from the full queue of waiting requests. All queued requests flooded in simultaneously, MySQL hit its real connection limit, and the problem compounded. The fix was counter-intuitive: shrink the pool back to ~1,000. That restored Vitess's ability to control admission, and throughput recovered.

**MY TAKE**

This is a textbook queueing theory failure that gets re-discovered at every company running a proxy in front of a database. The proxy is not just a connection multiplexer — it's an admission controller. When you raise the ceiling past MySQL's actual concurrency capacity, you eliminate the throttle entirely. What you actually want is a pool cap roughly aligned with the real connection limit, plus proper timeout and queue management on the proxy side. The instinct to "add more capacity" is deeply ingrained; it's correct when the bottleneck is the ceiling, and catastrophically wrong when the ceiling is load-shedding.

**THE TAKEAWAY**

Before you raise any queue or pool limit during an incident, ask one question first: what backpressure does this setting provide? Removing a limit often makes things worse, not better.

## AWS Dogwood — Temporal Auth for AI Agents

**THE PROBLEM**

Your AI agent calls 15 different tools over the course of a task. Some of those calls should depend on earlier steps — you shouldn't be able to send an email without first verifying the recipient, and you shouldn't be able to send more than three emails in a 10-minute window. Standard authorization systems check each action in isolation. They answer "can this agent call this tool now?" — but they can't answer "can this agent call this tool, given everything it has already done in this session?"

**WHAT THEY DID**

AWS built Dogwood, which extends Cedar with Metric First-Order Temporal Logic — a formalism from the runtime verification literature. A policy like "allow SendEmail only after VerifyRecipient has been called, and at most three times per 10-minute window" is a single Dogwood rule. In plain Cedar, that requires a bespoke side channel to track session history. Dogwood is open source under Apache 2.0, composes with existing Cedar policies without migration, and is now integrated into Amazon Bedrock AgentCore.

**MY TAKE**

The temporal dimension is the right primitive for agentic systems. Most authorization systems are stateless because stateless is cheap and consistent. But agents are inherently stateful — the sequence of actions matters. My concern is the state management problem hiding inside this design. Session history must be stored and queried at policy evaluation time. At high concurrency, that becomes a distributed systems problem in auth's clothing. What happens when session history is eventually consistent? The paper doesn't address it.

**THE TAKEAWAY**

If you're building multi-step AI agents today, design your authorization model around what the agent has *already done*, not just what it's requesting now. Dogwood is worth reading even if you're not on Cedar.

## Cloudflare Meerkat — Global Consensus

**THE PROBLEM**

You're running a distributed control plane across 300-plus locations globally. Raft requires a designated leader, and in a wide-area network, that leader may be unreachable to half your nodes at any moment. Leader-timeout elections cause availability loss. Make the timeout too short and you get false elections; too long and you wait out real failures. It's an inherent tradeoff.

**WHAT THEY DID**

Cloudflare built Meerkat on QuePaxa — a 2023 consensus algorithm by Tennage and Băsescu where all replicas can accept writes simultaneously, removing the leader-timeout availability hole entirely. Unlike Raft, progress is never blocked by waiting for an election timeout. Current scope is intentionally narrow: low-volume, high-stakes control-plane metadata — database leadership grants, AI model placement decisions, routing configuration. Cloudflare claims this will be the first industrial deployment of QuePaxa at global scale once it reaches production.

**MY TAKE**

The decision to start narrow is the right call and I'd argue it's the only responsible call. Consensus correctness bugs are catastrophic — they corrupt your coordination layer in ways that can be subtle and hard to detect until you have a split-brain. Testing QuePaxa at Cloudflare's 300-PoP topology using low-volume control-plane use cases first is the right proof-of-concept discipline. The gap between a 2023 academic paper and 300 real PoPs is large. The post-mortems from the next 12 months will be worth reading carefully.

**THE TAKEAWAY**

If you're running Raft in a geo-distributed system and hitting availability gaps during leader elections, QuePaxa is worth putting on your research list. Don't deploy it in production yet — let Cloudflare stress-test the industrial model first.

## Canva Session Revocation at Scale

**THE PROBLEM**

You have hundreds of millions of active sessions. A user logs out; an account gets compromised. You need to revoke that session immediately, and every subsequent auth check — across hundreds of application gateways — needs to enforce that revocation from that moment forward. At this scale, querying a database on every auth request is a bottleneck you can't sustain.

**WHAT THEY DID**

Canva moved to Amazon S3 as the durable revocation store and pushes compact, in-memory indexes to application gateways. The binary index format cut per-gateway revocation cache memory footprint by 87.5% compared to the previous approach, while also reducing read-replica infrastructure and speeding deployments. The separation is clean: S3 holds the authoritative record; gateways hold a lightweight derivation used for fast local checks.

**MY TAKE**

87.5% is a significant number — that's 8x fewer bytes per gateway to represent the same set of revoked sessions. The architectural split between write path (S3, durable) and read path (local index, fast) is textbook. The question I'd push on is propagation delay: when a new revocation is written to S3, how long until all gateways have updated their local index? In a security context, the window between "session revoked" and "all gateways enforce revocation" is an attack surface. Canva doesn't publish this number, which suggests it's either solved cleanly or was accepted as a deliberate tradeoff.

**THE TAKEAWAY**

Treat revocation propagation delay as a first-class security parameter in your auth system design, not an implementation detail you'll figure out later.

## WhatsApp On-Device Scam Detection

**THE PROBLEM**

You want to detect scam messages on a platform with a billion users. You can't do it server-side — the messages are end-to-end encrypted and you literally can't read them. So you have to do inference on the device. But then how do you measure whether it's actually working, without compromising the privacy properties that required on-device inference in the first place?

**WHAT THEY DID**

A lightweight ML model downloads to the device, classifies incoming messages from non-contacts locally, and zero message content leaves the device for inference. Efficacy measurement uses a confidential federated analytics pipeline running on confidential VMs — telemetry arrives at WhatsApp as differentially private aggregates. The system is designed for independent verifiability: model weights are published, manifests are signed by Cloudflare's transparency infrastructure, all model updates are logged in a third-party ledger, and users get an in-app audit log they can inspect.

**MY TAKE**

The verifiability stack is the genuinely interesting part. Publishing model weights and using signed manifests means a researcher can verify the model on their device is exactly what was published — this is trust-minimizing design done right. The weak point: the blog post claims differential privacy for the telemetry aggregates but doesn't publish epsilon and delta, which are the actual privacy parameters. "We use differential privacy" without the numbers is a technique description, not a guarantee. Those parameters determine how much signal leaks through the aggregation.

**THE TAKEAWAY**

On-device inference with transparent auditability is the right pattern for sensitive classification use cases. But if you claim differential privacy in your privacy documentation, publish the epsilon and delta values — otherwise you've named a technique, not made a guarantee.

## Wiz — Personal Repos as Corporate Attack Surface

**THE PROBLEM**

You've deployed enterprise secret scanning on your GitHub organization. You've locked down corporate repos. Your engineers have been through credentials hygiene training. You feel covered. Then Wiz Research publishes: 65% of the Forbes AI 50 had verified secret leaks, and 56% of company-impacting secrets were found not in enterprise repositories — but in employees' personal GitHub accounts. Outside the reach of your scanner entirely.

**WHAT THEY DID**

Wiz correlated personal GitHub repos to corporate developer identities, validated which exposed secrets were actually live and impactful, and found the attack surface is structural: engineers who push to a corporate GitHub Enterprise org by day maintain side projects under personal accounts at night, and when corporate code or credentials accidentally end up in personal repos, AI-assisted development accelerates the spread. AI coding assistants increase code reuse across contexts faster than manual review can catch.

**MY TAKE**

The AI acceleration angle is the uncomfortable one. An AI copilot doesn't know which context is the corporate one and which is the personal side project — it helps you move patterns, snippets, and configs across both. The organizational perimeter that made "secure the enterprise org" a coherent strategy broke down when developers started using tools that don't respect that perimeter. Wiz's solution — correlating personal to corporate identity and scanning across that boundary — is a reasonable detection layer. But it can't solve the underlying problem, which is cultural: engineers treat personal and work contexts as mentally adjacent when their tooling makes them physically adjacent.

**THE TAKEAWAY**

Enterprise secret scanning on your corporate GitHub org is necessary but no longer sufficient. If you're responsible for secrets management, your threat model has to include employees' personal repos.

## Google Post-Quantum Cryptography Roadmap

**THE PROBLEM**

Quantum computers capable of breaking RSA and elliptic-curve cryptography are not deployed today. But adversaries can harvest encrypted traffic now and decrypt it later — once quantum hardware exists. The clock on "harvest now, decrypt later" started years ago for sensitive data with long shelf lives. If your key management infrastructure, certificate authority chain, or customer SDK hasn't started PQC migration planning, you are already behind.

**WHAT THEY DID**

Google Cloud published their full PQC migration roadmap across three delivery domains: SNDL risk elimination by end of 2027, integrity and non-repudiation by 2028, and cryptographic key management foundations by 2028, with full platform coverage targeted for 2029 and legacy algorithm deprecation between 2030–2035. ML-KEM hybrid key exchange is already live on all google.com and googleapis.com endpoints and all load balancers. Cloud KMS already supports all three NIST PQC standards. The shared responsibility boundary is explicit: Google secures the infrastructure layer; customers own SDK updates, certificate authority reconfiguration, and their own application-layer cryptography.

**MY TAKE**

The shared responsibility framing is the most important sentence in that roadmap for enterprise teams, because it's where the gap lives. Most organizations will read "Google has deployed PQC on googleapis.com" and assume they're covered. They are not. Application-layer cryptography — data encrypted in your services using AWS KMS or your own key material, TLS termination on your own load balancers, certificates issued from your own CA — none of that is covered by Google's infrastructure migration. The 2030–2035 deprecation timeline looks far away until you account for the fact that replacing cryptographic primitives across a large org's software estate takes years.

**THE TAKEAWAY**

If you haven't started a PQC migration inventory — cataloging where your systems use RSA or EC cryptography and assessing which data has long-term sensitivity — start now. 2030 is closer than it looks when measured in enterprise migration time.
