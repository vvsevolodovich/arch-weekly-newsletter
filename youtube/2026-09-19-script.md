## Neki — Sharded Postgres at 118M QPS

**THE PROBLEM**

You've probably tried to scale Postgres beyond what a single node can handle. The options are ugly: read replicas that help with reads but not writes, manual sharding that you own forever, or migrating to a system that isn't Postgres at all. Vitess solved this for MySQL — horizontal sharding with online resharding, automatic failovers, schema migrations that don't lock tables — but Postgres users have been waiting years for something equivalent. The gap wasn't about performance. It was about the operational primitives you need to run sharded Postgres in production without a 3am incident.

**WHAT THEY DID**

PlanetScale published the benchmark for Neki, their sharded Postgres product: 118.5 million queries per second, 200,000 QPS per shard across 512 shards, 1.22 petabytes of data. The architecture is Vitess-ported to Postgres: Neki routers speak the Postgres wire protocol and handle cross-shard query planning, with per-instance connection pooling sidecars and a control plane managing failovers and resharding. Each shard is a full Postgres cluster with one primary and two replicas across three availability zones. Schema changes, failovers, version upgrades, imports, and resharding all run as online workflows — the same operational model that made Vitess compelling for MySQL users.

**MY TAKE**

The benchmark caveats matter: read-only workload, primaries with no replicas running, no failovers during the measurement window. 118M QPS under those conditions is a ceiling, not a typical operating point. What the benchmark actually demonstrates is that the routing layer isn't the bottleneck — the QPS scales linearly with shard count, which means the architectural model is sound. The operationally interesting claims aren't in the benchmark. They're in "online resharding" and "zero-downtime schema changes" — which are the things that make sharded databases a maintenance nightmare in practice. I'd want to see the failure modes stress-tested before trusting this in production.

**THE TAKEAWAY**

If you're at the point where Postgres read replicas aren't enough and you're evaluating sharding options, Neki is worth a serious look — specifically because it inherits Vitess's operational model, not because of the QPS headline.

## TIN + Lead — Postgres Full-Text Search

**THE PROBLEM**

You've probably built full-text search on Postgres using tsvector, hit a wall, and then had a long conversation about whether to stand up Elasticsearch. The wall looks different depending on what you hit first: tsvector doesn't replicate correctly because the derived column updates lag behind the base table, it doesn't maintain transactional consistency, and schema changes require a full reindex with a lock. Meanwhile, you can't easily run the same search queries in CI or development without a full Postgres instance configured exactly like production.

**WHAT THEY DID**

PlanetScale shipped TIN: a full-text search extension for Postgres that addresses the replication and transaction problems directly. TIN is 3 to 30 times faster than competing Postgres FTS indexes, works correctly under replication and backup workflows, and maintains proper transaction visibility — a search query sees exactly what a regular query sees at the same transaction snapshot. The same day, they shipped Lead: an open-source, feature-equivalent version of TIN designed for CI, development, and staging environments. Lead runs fully offline, supports the same SQL statements and TINQL searches, and is free. TIN is production; Lead is dev/test parity.

**MY TAKE**

The dev/test parity story is the part most write-ups missed. The reason teams end up with Elasticsearch isn't always because tsvector is too slow — it's because integrating Postgres FTS correctly into a test suite is painful enough that teams eventually give up and mock it out. Once you're mocking search in tests, you're not testing your search logic, and that gap bites in production. Lead is the piece that makes TIN actually adoptable: if your CI runs Lead, your search integration tests are testing real behavior, not stubs.

**THE TAKEAWAY**

If you're using tsvector today and hitting replication or consistency problems, evaluate TIN. And if you're avoiding Postgres FTS because of the dev/CI friction, Lead removes the main objection.

## Cloudflare — 100TB Freed With Rust

**THE PROBLEM**

You're running a service across a fleet of tens of thousands of servers. One of the data structures in the hot path is subtly overallocated — each instance uses a few hundred extra bytes that nobody notices, because it's not a leak and it's not a bug. But multiply it across the fleet and you have a number with a lot of zeroes. The problem doesn't show up in local profiling, and no single instance causes an alarm. This is the class of problem that only becomes visible when someone decides to look at it globally.

**WHAT THEY DID**

Cloudflare's Pingora Backend Router uses pingora-ketama for consistent hashing across backend servers. Two optimizations freed 100 terabytes globally. First: a Rust struct repack. Fields were arranged in an order that caused the compiler to insert alignment padding. Moving them to eliminate that padding cut the struct's memory footprint by 25%. Second: a statistical analysis of how many virtual nodes per server ketama actually needed for consistent hash distribution. The default was 160 virtual nodes. Running the math showed that 16 virtual nodes gave nearly identical distribution with 10 times less memory. Together: 100TB freed across the fleet without any change to behavior.

**MY TAKE**

The ketama insight is the generalizable one. Most implementations of consistent hashing copy the virtual node count from the original paper or from the first implementation they saw — 150, 160, whatever the reference used. Nobody asks how many you actually need for your fleet size and key distribution. Cloudflare ran the statistics and found the answer was an order of magnitude lower. The struct alignment issue is more mundane but just as illustrative: at fleet scale, the compiler's padding decisions aren't your problem until they suddenly are. Rust's memory layout is deterministic, which is what made it debuggable.

**THE TAKEAWAY**

Before you buy more RAM, profile your data structures at fleet scale. Alignment padding and default configuration values that nobody questioned are often the culprits, and fixing them is free.

## Client-Side Security — Malicious JS Campaign

**THE PROBLEM**

You scan your JavaScript dependencies at install time. You run VirusTotal checks on suspicious URLs. You feel covered. Then attackers stop putting the malicious code in the file and start loading it at runtime — conditionally, based on browser fingerprint, time of day, whether you're running in a headless browser, whether the visitor looks like a bot. The file you scanned is clean. The behavior at runtime is not. Static scanners check what's in the file. They can't check what the file decides to do.

**WHAT THEY DID**

Cloudflare's Page Shield uses a graph neural network to map how scripts interact with the page's DOM elements, read form fields, and make outbound network calls — behavioral analysis, not signature matching. When the GNN flags a pattern as anomalous, an LLM triage layer reviews the behavior and a frontier model confirms. This week, they published case studies on four malicious campaigns spanning eight payloads. Seven of eight were completely absent from VirusTotal. None were flagged by URLScan. The campaigns included affiliate revenue hijacking, click and analytics manipulation, and a loader that asked a remote server what code to execute next — content that would never show up in a static scan.

**MY TAKE**

The 7/8 miss rate on VirusTotal is the number that should change how you think about client-side security posture. VirusTotal is useful for known-bad. It's not useful for condition-dependent, dynamically-loaded, first-party-signed scripts that behave differently in a headless scanner than they do in a real browser. The GNN approach works because it models the relationship between scripts and page elements — which is the actual threat surface, not the script in isolation. The LLM triage layer is the part I'd watch: at scale, the false positive rate on behavioral anomaly detection is the thing that makes this operationally viable or not.

**THE TAKEAWAY**

Static dependency scanning on install is necessary but covers a different threat than runtime behavioral analysis. If you're operating an e-commerce storefront or handling payment flows, client-side behavioral monitoring is a separate control, not a redundant one.

## GitHub HydraFusion — Multi-Model Routing

**THE PROBLEM**

You've deployed a frontier AI model for code generation. Simple autocomplete is routed to the same model as complex multi-file refactors. You're paying frontier prices for tasks a model one-tenth the cost could handle correctly. The problem: you don't know at request time which tasks are easy and which are hard. Routing to a cheaper model first and escalating on failure sounds right, but cascade errors that fail silently are worse than using the expensive model in the first place.

**WHAT THEY DID**

GitHub HydraFusion classifies each coding task at runtime into one of three execution patterns. Single: one model, no overhead. Cascade: a cheap model attempts first; escalates to a more capable model if the output doesn't pass confidence checks. Critique: a small model drafts a solution and a separate model reviews and revises it. Model selection is cross-provider, mixing models from different vendors within one workflow. Benchmark results on TerminalBench 2.1: 67% cost reduction versus routing everything to Claude Opus 5, with a 4.9 percentage point improvement in task completion. The system is available in GitHub Copilot CLI as an experimental flag.

**MY TAKE**

67% cost reduction with a benchmark improvement is the counterintuitive result. The normal expectation is that cheaper routing trades off quality. The explanation is that the optimal model for a task is not always the most capable one — a task that's fully within a smaller model's competence gets more consistent outputs from that model than from a frontier model that's over-parameterized for the task. The critique pattern is the one I find most interesting architecturally: it's not about model capability, it's about error surface. Two models reviewing each other reduces the probability that both models make the same mistake.

**THE TAKEAWAY**

If you're building AI agent pipelines today, task complexity classification is a first-class design concern. Routing everything to the most capable model is not a safe default — it's an expensive one that doesn't necessarily produce better outputs on simple tasks.

## AWS MCP — Deleting Your Session Store

**THE PROBLEM**

You built an MCP server. Following the pre-July spec, you needed stateful sessions: every client initiated with a handshake, received a session ID, and echoed that ID on every subsequent request. On AWS, this meant sticky load balancer routing or an external session store — Redis, Elasticache — so any instance could serve any session. You've been running this infrastructure and paying for it since you shipped. Now the protocol changed.

**WHAT THEY DID**

MCP specification 2026-07-28 removed the initialize handshake and the Mcp-Session-Id header entirely. Every request now carries its own protocol version and client context. A client's first message can be the actual tool call, and any server instance can respond to it — no session affinity required. On AWS, this means: delete the Elasticache session store, disable sticky routing on your load balancer, and run your MCP servers as plain stateless Lambda functions or ECS tasks. The AWS Architecture Blog published a full Well-Architected mapping of the new design across all five pillars, showing exactly which infrastructure components are now safe to remove.

**MY TAKE**

The protocol change is architecturally correct. Statefulness at the transport layer was fighting the horizontal scaling model of every major cloud provider. The practical problem is migration: if you're running McpAgent on Cloudflare Workers, those Durable Object sessions are the thing you're moving away from. If your MCP clients haven't updated to the 2026-07-28 spec, they'll still send Mcp-Session-Id headers your server now ignores — that needs testing before you remove the infrastructure. The simplification is real, but the migration has a sequencing problem that the spec change glosses over.

**THE TAKEAWAY**

If you deployed MCP servers before July 28, 2026, you likely have session infrastructure you can now remove. Verify your clients are on the new spec first, then work through the Well-Architected mapping to identify what's safe to delete.

## Stripe — Building a Proxy From Scratch

**THE PROBLEM**

You're running a service mesh proxy. It works fine. Then your traffic grows to a point where the proxy's concurrency model becomes the ceiling. At Stripe — 1.6% of global GDP flows through their payment infrastructure — Envoy's model of one worker per CPU core was opening hundreds of thousands of simultaneous connections to backend services. Not because the traffic required it. Because of how Envoy manages connection state: each worker maintains its own connection pool to each upstream, which means connection count scales with workers times upstreams, not with actual concurrent requests.

**WHAT THEY DID**

Stripe replaced Envoy with mesh-proxy: a Go service that ships its own HTTP/1.1 and HTTP/2 implementation, talks directly to their service registry for discovery, and runs one read goroutine and one write goroutine per connection. Multiple requests multiplex over a single shared connection to each upstream. Connection count now scales with actual upstream relationships, not with worker count. The Go concurrency model let them multiplex cheaply. They also needed routing semantics that would have required heavy Envoy extension development — building from scratch meant those semantics were first-class in the design.

**MY TAKE**

This is the "outgrew the tool" story in its cleanest form. Envoy is an excellent general-purpose proxy, and the connection count problem was solvable inside Envoy's threading model to a point. Stripe hit the point. The Go choice means they own the HTTP stack entirely — every edge case in HTTP/1.1 connection management, every HTTP/2 flow control interaction, is now their problem. That's a significant ongoing maintenance cost. But it also means they got to build the routing semantics they actually needed instead of fitting their requirements into Envoy's extension API.

**THE TAKEAWAY**

A service mesh proxy is a ceiling, not a floor. Before you build your own, the question is whether your routing requirements and concurrency model fit within the extension model of what's available. At Stripe's scale and routing complexity, they didn't. At your scale, they probably do.
