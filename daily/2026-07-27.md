## [How MVCC and Transactions Work in RocksDB](https://artem.krylysov.com/blog/2026/07/23/how-mvcc-and-transactions-work-in-rocksdb/) 🤓

RocksDB's LSM-tree design — where every write creates a new immutable key version rather than modifying in-place — supplies the raw material for MVCC: sequence numbers tag each version, SuperVersions track the live SST file set, and snapshots give readers a consistent point-in-time view without blocking writers. Compaction acts as garbage collection, purging versions no longer reachable by any open snapshot. Transactions layer on top in two modes: optimistic (validate at commit, low overhead for read-heavy low-contention workloads) and pessimistic (per-key locks held throughout, for contended hot keys) — but range locks must be managed explicitly to prevent phantom reads, and all locking is strictly node-local, which is why databases like CockroachDB and TiKV must add a distributed coordination layer above RocksDB's transaction API. #db #architecture #engineering

## [Modernizing the Meta Ads Service With an Open-Source Kernel Scheduler](https://engineering.fb.com/2026/07/13/ml-applications/modernizing-the-meta-ads-service-with-an-open-source-kernel-scheduler/) 🤓

Meta's ads retrieval fleet handles 5 million requests per second — over 400 billion per day — and the team deployed sched_ext, a BPF-based extensible scheduler class merged into Linux kernel v6.12, to replace the default CFS with a custom policy tuned to their bursty, latency-sensitive retrieval workload. Rather than forking Linux or maintaining large patch sets, sched_ext lets operators define a complete scheduling algorithm as a BPF program with the same kernel safety guarantees; Meta adapted SCX-LAVD (originally designed for Valve's Steam Deck to minimize tail latency on heterogeneous cores) to their data center context. Fleet-scale results: 28% reduction in p99 ads retrieval latency, 3.28 MW in power savings, and a 1.1% increase in the number of ads ranked per request. #architecture #engineering #softwareengineering

## [PostgreSQL on Azure: Two services, one future-proofed ecosystem](https://techcommunity.microsoft.com/blog/adforpostgresql/postgresql-on-azure-two-services-one-future-proofed-ecosystem/4536578) 👨‍💼

Microsoft has clarified its two-track Postgres cloud strategy: Azure Database for PostgreSQL Flexible Server remains the general-purpose, open-source-compatible offering, while Azure HorizonDB targets elastic, AI-era workloads with a rebuilt cloud-native architecture. HorizonDB uses a log-centric storage model where the PostgreSQL write-ahead log is the sole persistence mechanism — compute nodes never write data pages to disk directly, treating them as derived state reconstructed from WAL records by a dedicated storage fleet split into a WAL-storage tier (low-latency writes) and a page-storage tier (high-throughput reads). The scale envelope: up to 3,072 vCores across primary and read replicas, 128TB databases, sub-millisecond multi-zone commit latencies, and read replicas that share a single copy of pages from the storage layer rather than maintaining their own. #db #cloud #architecture #engineering
