## [Concurrency vs. Throughput: Why More Parallelism Can Make Databases Slower](https://planetscale.com/blog/concurrency-vs-throughput-vitess-mysql) 🤓

When a single long-running query blocked Vitess's vttablet transaction pool, the instinct was to raise the pool ceiling from ~1,000 to 10,000 — but this removed backpressure, allowing the full queue of waiting requests to flood MySQL simultaneously and compound the problem. Vitess's backpressure mechanism only functions when the transaction pool cap is kept roughly aligned with MySQL's true connection capacity; once the cap vastly exceeds that, vttablet loses the ability to throttle inbound load before it reaches the database engine. The fix was counter-intuitive: shrinking the pool back to ~1,000 restored Vitess's ability to control admission, and throughput recovered — demonstrating that queue depth at a proxy layer is a first-class architectural parameter, not just a ceiling to raise when errors appear. #db #distributed #architecture #engineering

## [GOL! How TelevisaUnivision Streamed the FIFA World Cup to 675 Million Views](https://cloud.google.com/blog/products/networking/streaming-the-fifa-world-cup-with-televisaunivision) 👨‍💼

Delivering 104 live matches at 100% availability across 39 consecutive days required two structural decisions: in-ISP deep edge caching with direct peering to América Móvil and Telefônica rather than relying solely on CDN PoPs outside ISP networks, and migrating the session store to Memorystore for Valkey 9.0 running as serverless microservices with sub-millisecond authentication latency. Origin infrastructure was protected from the full volume of 675 million cumulative views by absorbing traffic at the ISP edge, exposing the origin only to cache misses. Joint 24/7 war rooms between TelevisaUnivision and Google Cloud Customer Reliability Engineering, with pre-tournament stress testing and live CDN reconfiguration during matches, translated the architectural resilience into zero-incident execution — a deployable blueprint for any marquee live-streaming event. #cloud #architecture #engineering #devops

## [Unbiased Java CPU Profiling with JFR in JDK 25](https://www.datadoghq.com/blog/engineering/jfr-cpu-time-profiling/) 🤓

JFR's `ExecutionSample` event collected samples without weighting them to actual CPU time, causing some hotspots to appear under- or over-represented relative to their true cost — a bias that made profiling results misleading for CPU-bound production workloads. JDK 25 introduces a first-class CPU-time profiling event built on cooperative stack walking: rather than immediately unwinding the stack at the signal-handler boundary (the approach that required fragile access to unsupported JVM internals via `AsyncGetCallTrace`), the new mechanism defers capture to a safe state between any instruction and the next safepoint where JVM structures are guaranteed stable. The result is accurate, proportional CPU sampling that requires no unsupported APIs — eliminating the instability risks that forced production profilers to depend on internal JVM mechanisms, with native frame capture and on-demand stack capture for latency spikes already in the development pipeline for future JDK releases. #engineering #softwareengineering #quality #development
